## 3. 파일 구조

> ⚠️ 저장소에 확장자 없는 구버전 `crossway_environment` 파일이 남아 있다.
> **`crossway_environment.py`(수정본)가 최신**이며, 환경을 고칠 때는 반드시 이쪽을 고칠 것.
> 구버전은 아래 4절의 문제들이 수정되기 전 버전이다.

| 파일 | 역할 |
|---|---|
| `env_config.py` | **환경 설정 전부** (교통량, 신호 시간, 페이즈 구성, 보상). 실험 조건은 여기서 바꾼다 |
| `crossway_environment.py` | 교차로 시뮬레이션 로직 (팀 공용, **수정본**). Gym 스타일 `reset()` / `step(action)` |
| `q_learning_agent.py` | Q-table 기반 에이전트 |
| `dqn_agent.py` | PyTorch DQN (Experience Replay + Target Network) |
| `train_dqn.py` | DQN 학습, 모델을 `results/`에 저장 |
| `evaluate.py` | 성능 지표 측정 및 기준선 비교 |
| `visualize.py` | tkinter 실시간 시각화 |
| `results/` | 학습된 모델(.pt), 학습 이력·평가 결과(.json) |
| `.env.example` | API 키 보관 파일 견본 (아래 6절) |

새 알고리즘을 추가하려면 환경만 가져다 쓰면 된다:

```python
from crossway_environment import CrosswayEnvironment, STAY, SWITCH

env = CrosswayEnvironment(preset="normal", seed=0)
state = env.reset()
next_state, reward, done, info = env.step(STAY)
```

### 교차로 모델

- 진입로 4개(북·남·동·서) × 신호를 받는 이동류 2개(직진·좌회전) = **대기열 8개**
- 우회전은 신호와 상관없이 바로 통과한다고 본다 (대기열 없음)
- 한국처럼 우측통행. 각 진입로에 좌회전 차로(중앙선 쪽)와 직진 차로(바깥쪽)가 있다
- 초록불인 차로마다 초당 0.5대가 빠져나간다 (차로 하나의 처리 능력 ≈ 1,800대/시간)
- 차마다 도착 시각을 기록해서, 통과할 때 실제 대기시간을 잰다

**state** (기본, 10개 값):
`(북직진, 북좌회전, 남직진, 남좌회전, 동직진, 동좌회전, 서직진, 서좌회전, 페이즈, 유지시간)`

`state_mode="simple"`로 바꾸면 예전처럼 `(남북 합계, 동서 합계, 페이즈, 유지시간)` 4개 값이 된다.

## 3-1. 환경 바꾸는 법 (팀원용)

로직 파일(`crossway_environment.py`)은 건드릴 필요 없다. 바꾸고 싶은 값을 넘기기만 하면 된다.
모든 항목의 설명은 `env_config.py`의 `EnvConfig`에 적혀 있다.

```python
from crossway_environment import CrosswayEnvironment
from env_config import make_config

# ① 프리셋 그대로: night / normal / rush_hour / ns_heavy
env = CrosswayEnvironment(preset="rush_hour", seed=0)

# ② 프리셋에서 일부만 바꾸기
env = CrosswayEnvironment(preset="normal", min_green=10, switch_penalty=1.0, seed=0)

# ③ 방향별 교통량 직접 지정 (대/시간)
env = CrosswayEnvironment(preset="normal",
                          arrival_per_hour={"N": 900, "S": 900, "E": 300, "W": 300})

# ④ 직진·좌회전·우회전 비율 바꾸기 (합이 1이어야 함)
env = CrosswayEnvironment(preset="normal",
                          turn_ratio={"straight": 0.85, "left": 0.15, "right": 0.0})

# ⑤ 예전 방식(상태 4개)으로 실험
env = CrosswayEnvironment(preset="normal", state_mode="simple")
```

자주 바꿀 만한 항목:

| 항목 | 기본값 | 설명 |
|---|---|---|
| `arrival_per_hour` | 프리셋 | 진입로별 시간당 진입 대수 |
| `turn_ratio` | 34/33/33 | 직진·좌회전·우회전 비율 |
| `pass_rate` | 0.5 | 초록불 차로에서 초당 빠져나가는 대수 |
| `phases` | 4페이즈 | 페이즈 구성과 순서. 페이즈를 추가하거나 순서를 바꿀 수 있다 |
| `min_green` | 15 | 최소 초록시간(초) |
| `max_cycle` | 120 | 한 바퀴 주기의 상한(초). 페이즈당 최대 = 120 / 페이즈 수 |
| `episode_seconds` | 600 | 에피소드 길이(초) |
| `reward_mode` | `"queue"` | `"delta"`는 연구계획서 원안 (4절 참고) |
| `switch_penalty` | 0.5 | 신호를 바꿀 때마다 빼는 점수 |
| `state_mode` | `"movement"` | `"simple"`은 상태 4개 |

설정을 잘못 넣으면(비율 합이 1이 아님, 어느 페이즈에도 없는 이동류 등) 실행 즉시 어디가 틀렸는지 알려준다.

> ⚠️ `state_mode`나 페이즈 수를 바꾸면 상태 크기가 달라지므로, 기존 DQN 모델(`results/*.pt`)은 쓸 수 없다.
> 바꾼 설정으로 `python train_dqn.py`를 다시 돌려야 한다. 맞지 않는 모델을 불러오면 오류로 알려준다.

## 4. 스펙에서 바뀐 점 (중요 — 보고서에 반영 필요)

구현하며 연구계획서 원안의 문제 세 가지를 발견해 수정했다.

**① 보상 함수** — 원안 `reward = -(대기열 증가분)`은 한 에피소드 동안 더하면
중간 항이 상쇄되어 `-(마지막 대기열)`만 남는다. 중간에 얼마나 막혔는지가
보상에 반영되지 않아, DQN이 "전환을 최대한 안 하기"만 학습해 평균 대기열이
오히려 8.4대 → 11.6대로 **악화**됐다.
→ 대기열의 *수준*을 벌하는 `reward_mode="queue"`를 기본값으로 바꿨다.
원안은 `reward_mode="delta"`로 남아있으니 **두 보상 설계 비교 자체를 실험 결과로 쓸 것.**

**② 할인율(gamma)** — 0.9는 1초 스텝에서 약 10초 앞만 본다. 신호 한 주기가
60~120초라 에이전트가 자기 결정의 결과를 볼 수 없었다. → 0.99로 변경.

**③ "전체 신호 주기 최대 120초"의 해석** — 이건 4페이즈를 한 바퀴 도는 시간의
상한이지 에피소드 길이가 아니다. → 페이즈당 최대 30초 강제 전환(`max_cycle / 페이즈 수`)으로
구현하고, 에피소드 길이는 `episode_seconds=600`으로 분리했다.

**④ 방향별 교통량 분리** — 남북/동서 교통량이 같으면 "바로 전환"이 최적이라
적응형 제어가 이길 여지가 구조적으로 없다(실제로 DQN이 고정주기와 완전히 동일한
정책을 학습했다). 실제 교차로에서 적응형 신호가 쓰이는 이유는 방향별 교통량이
다르기 때문이므로 진입로별 교통량(`arrival_per_hour`)을 따로 둔다.

**⑤ 상태를 8개 이동류로 분리** — 원안의 상태(남북 합계, 동서 합계)로는 줄 선 차가
직진인지 좌회전인지 알 수 없다. 신호는 직진과 좌회전이 따로 켜지므로 이를 구분해야
제대로 판단할 수 있다. → 4방향 × (직진, 좌회전) = 8개 대기열을 상태로 쓴다.
같은 30 에피소드 학습 후 Q-table 크기가 **331개(상태 4개) → 6,237개(상태 10개)**로
19배 커졌다. 상태공간이 커질수록 Q-learning이 불리해진다는 가설의 직접적인 근거가 된다.

**⑥ 평균 대기시간을 직접 측정** — 이전에는 `평균 대기열 ÷ 처리율`(리틀의 법칙)로
추정했다. 이제 차마다 도착 시각을 기록해 `통과 시각 − 도착 시각`의 평균을 낸다.

**⑦ 교통량 단위를 대/시간으로** — 실제 교통량 데이터(공공데이터)와 단위를 맞추기 위해
'초당 도착 확률' 대신 '진입로별 시간당 대수'로 설정한다.

## 5. 현재 성능 (evaluate.py, normal 프리셋, 60 에피소드 평균)

8방향 환경, 상태 10개, DQN 150 에피소드 학습 기준.

| 시나리오 | 정책 | 평균 대기열 | 평균 대기시간 | 전환 횟수 |
|---|---|---|---|---|
| 대칭 교통량 | 고정주기 15초 | 9.48대 | 21.6초 | 37.0 |
| | DQN | 9.69대 | 22.0초 | 36.2 |
| 비대칭 (남북 편중) | 고정주기 15초 | 10.91대 | 24.7초 | 37.0 |
| | DQN | 10.92대 | 24.7초 | 37.0 |

DQN이 "최소 시간(15초)이 지나면 바로 전환"하는 정책을 학습해서 고정주기 15초와 거의 같다.
normal 프리셋은 처리 능력의 절반 정도만 차는 교통량이라, 빨리 돌려주는 것이 사실상 최선이다.

> 이전 버전(상태 4개)에서 비대칭 교통량일 때 DQN이 2.6% 이겼던 결과는 환경 모델이 달라서
> 직접 비교할 수 없다. 새 모델은 초록불인 차로마다 따로 차가 빠져나가므로(양방향 동시 통행)
> 같은 교통량에서도 덜 혼잡하다.

적응형 제어의 이득은 교통량이 처리 능력에 가까울 때 나타날 가능성이 크다.
다음 실험은 `rush_hour` 프리셋으로 학습·평가해서 이를 확인하는 것이다.
